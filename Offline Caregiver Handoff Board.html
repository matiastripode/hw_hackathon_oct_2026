Offline Caregiver Handoff Board

A private, local-first web app hosted on a Raspberry Pi that helps one caregiver hand off medications, symptoms, appointments, tasks, and concerns to the next — with zero internet.

1Executive summary

The Pi broadcasts its own Wi‑Fi network. Caregivers join from phones, tablets, or laptops via a printed QR code, sign in on a dummy login screen, record care updates, and submit a shift handoff that the next caregiver acknowledges. A small physical indicator makes the Pi part of the product, not just a server.

Core workflow

  1. Caregiver signs in (dummy login) and opens the patient dashboard.
  2. They record a medication, symptom, task, appointment, or concern.
  3. They submit a handoff with a free‑text note.
  4. Next caregiver signs in on another device and sees what changed, what's complete, and what still needs attention.
  5. Next caregiver acknowledges the handoff; the physical indicator clears.

2Product goals

Goals

  • Handoffs readable in under 30 seconds
  • Unresolved concerns surfaced without searching
  • Multiple devices at once, near‑live updates
  • No internet, no external APIs, no CDN assets
  • Meaningful use of Pi hosting and hardware
  • Buildable and demoable during the hackathon

Out of scope

  • Diagnosis or clinical recommendations
  • Real patient data / PHI
  • Cloud sync
  • SMS, email, push, external integrations
  • Billing, payments, insurance
  • Real authentication (login is a dummy)
  • Complex permissions / multi‑org admin

3Features (MVP)

Dummy login screen New

  • Shown on first visit and after sign‑out.
  • Pick a seeded caregiver (Maria, Alex) or type a display name; password field accepts anything.
  • Session cookie stores the name, used as author on entries and handoffs.
  • Labeled "Demo login — no real authentication."
  • Sign‑out in header to switch caregivers on one device.

Patient dashboard

  • Patient header (fictional: James, age, key notes).
  • Open items grouped by type, sorted by severity; unresolved concerns pinned on top.
  • Quick‑add form: type, title, details, severity, status.
  • Live refresh via Server‑Sent Events (fallback: poll every 5 s).

Handoff

  • "Submit handoff" → note + snapshot of changes since the last acknowledged handoff.
  • Summary: Completed · Changed · Still needs attention · Note + author + timestamp.
  • "Acknowledge handoff" closes the shift boundary.

Physical indicator Hardware

Pick based on parts available, in priority order:

  1. LED on GPIO — on while a handoff is unacknowledged or a high‑severity concern is open.
  2. Button on GPIO — acknowledges the latest handoff.
  3. e‑ink / LCD — open‑concern count and last handoff time.

Hardware code sits behind a small interface with a no‑op fallback so the app also runs on a laptop.

Always‑visible disclaimer

"Prototype — fictional data only — not medical advice."

4Data model

One unified entry table instead of five separate features.

TableFields
caregiverid, name
entryid, type (medication | symptom | task | appointment | concern), title, details, severity (low | medium | high), status (open | done), value, previous_value, author, created_at, updated_at
handoffid, author, note, submitted_at, acknowledged_by, acknowledged_at
  • previous_value enables trends like "Dizziness: mild → moderate".
  • "Changed" = entries created/updated after the last acknowledged handoff's acknowledged_at.

5Architecture

App

  • Single process: FastAPI (or Express)
  • SQLite in WAL mode
  • Server‑rendered HTML + htmx
  • All JS/CSS/fonts bundled locally
  • SSE for live updates
  • systemd auto‑start on boot

Network

  • Pi runs its own Wi‑Fi hotspot (NetworkManager)
  • Reachable at http://handoff.local + fixed IP fallback
  • Printed QR codes: Wi‑Fi join + URL

Time

  • Pi has no RTC and no NTP offline
  • Preferred: DS3231 RTC HAT
  • Fallback: adopt first client's browser time on boot (/api/clock-sync)

6Primary demo scenario

Evening shift. Maria signs in on her phone while caring for her father, James. She records his 8:00 PM medication as taken, updates dizziness from mild to moderate, marks tomorrow's cardiology appointment as needing transportation confirmation, and submits a handoff note. The LED turns on.

Morning shift. The morning caregiver signs in from a laptop and immediately sees:

Handoff from Maria8:42 PM
8:00 PM medication — completed
Dizziness — mild → moderate (unresolved)
Cardiology appt tomorrow — transportation needs confirmation
"Dad was a bit unsteady after dinner. Please check in on dizziness first thing."

They acknowledge the handoff (on screen or via the physical button). The LED turns off. Everything happens on the Pi's own network with the internet disconnected.

7Success criteria

  • 3‑minute demo across 2 devices runs end to end with no internet
  • Handoff summary readable in under 30 seconds
  • Second device reflects changes within ~5 s without manual refresh
  • Timestamps correct on an offline boot
  • One‑command seed/reset restores the fictional demo state

8Build plan

  1. Scaffold app, SQLite schema, seed/reset script, disclaimer banner
  2. Dummy login + session cookie + sign‑out
  3. Dashboard + quick‑add entry + status/severity updates
  4. Handoff submit / summary / acknowledge
  5. SSE live updates
  6. Pi setup: hotspot, mDNS, systemd, clock strategy
  7. GPIO indicator (LED → button → display as time allows)
  8. Rehearse demo offline; print QR codes
